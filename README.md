# 家宴点菜小程序 · 部署手册

一个自研的微信小程序（云开发版），给朋友扫码点菜用。
主人先录好菜库 → 上架今晚的菜 → 朋友扫码点单（数量 + 口味备注 + 人数）→ 主人在后厨看板看汇总，导出清单发给家人备菜。

- **技术栈**：微信小程序原生 + 微信云开发（云函数 + 云数据库）
- **现金成本**：注册 0 元、认证 0 元（个人主体免认证费）、云开发最低档约 20 元/月
- **不需要的东西**：服务器、域名、ICP 备案、微信支付、公众号
- **代码位置**：`D:\ai\DeepSeek\family-dinner-miniapp`

---

## 一、为什么是云开发（而不是你那台服务器）

小程序的 `wx.request` 只能请求**已在工信部 ICP 备案**的 HTTPS 域名，微信公众平台配置服务器域名时也会校验备案。
你那台有公网 IP 的服务器如果没有备案域名，小程序根本调不通；域名备案要 1–2 周，本周末来不及。

微信云开发把数据库和云函数都放在微信自己的环境里，**不经过服务器域名白名单**，所以免备案、免运维，还能长期复用。

## 二、部署步骤（约 30 分钟，一次做完）

### 第 1 步：注册小程序，拿到 AppID

1. 打开 https://mp.weixin.qq.com → 「立即注册」→ 选「小程序」
2. 用一个**没有注册过公众号/小程序**的邮箱注册并激活
3. 主体类型选「个人」，用身份证 + 微信扫码做人脸核身
4. 登录后台 → 「开发」→「开发管理」→「开发设置」→ 复制 **AppID(小程序ID)**

> 个人主体小程序**不需要** 300 元/年的认证费，也不需要选服务类目——体验版不走审核。

### 第 2 步：装微信开发者工具

下载「稳定版 Windows 64」：https://developers.weixin.qq.com/miniprogram/dev/devtools/download.html
安装后用**小程序管理员**的微信扫码登录。

### 第 3 步：导入项目

1. 打开开发者工具 → 「+」→「导入项目」
2. **目录**选：`D:\ai\DeepSeek\family-dinner-miniapp`
3. **AppID**：已经预填在 `project.config.json` 里（`wxce5fca623936edf9`），工具会自己读出来；如果显示为空或报 AppID 错误，手动粘贴一次即可
4. 后端服务选「微信云开发」→ 点「导入」

导入后应该能看到左侧 `miniprogram` 目录和带云朵图标的 `cloudfunctions/api`。

### 第 4 步：开通云开发

1. 点工具栏的「云开发」→ 按引导开通 → 新建环境，名字随意（如 `family-dinner`）
2. 记下**环境 ID**（形如 `family-dinner-8gxxxxx`，在云开发控制台左上角环境名旁）
3. 如果你有**多个**云环境，把环境 ID 填进 `miniprogram/config.js` 的 `envId`；只有一个环境就留空

> 云开发现在是按量/包月付费（最低档约 20 元/月，以控制台实际报价为准）。家宴结束后可以在控制台停用/退订，不留后患。
>
> **只有一个云环境时，`miniprogram/config.js` 的 `envId` 留空即可**（会自动使用默认环境）。
> 如果你建了多个环境，或者运行时看到报错里提到 `env`，就把环境 ID 填进 `config.js` 的 `envId`。

### 第 5 步：部署云函数

1. 在左侧文件树右键 `cloudfunctions/api` → 「上传并部署：云端安装依赖（不上传 node_modules）」
2. 等右下角提示上传成功（第一次约 1 分钟）
3. **建议**：云开发控制台 → 云函数 → `api` → 配置 → 把**超时时间改成 20 秒**，保存

> 只有这一个云函数。为了减少出错点，所有接口都用 `action` 路由写在同一个函数里，不需要逐个部署。

### 第 6 步：初始化家宴

1. 点工具栏「编译」，模拟器里会出现「家宴还没开通」
2. 切到「我的点单」页 → 点「我是主人，一键开通」→ 你成为管理员，并生成 4 位**主人口令**
3. 进入「家宴设置与菜库」：
   - 填家宴标题、主人称呼、地址、给朋友的一句话
   - 设**点单截止时间**（比如周六 10:00），保存
   - 点「导入内置菜库」→ 69 道菜入库（**默认全部下架**，接着要勾选今晚的菜）
   - 默认已上架 14 道经典家宴菜，**按今晚实际菜单逐道勾选**（10 人桌一般 12～14 道）
   - 想限量的菜填个数字，比如「红烧狮子头 限 3 份」

### 第 7 步：发布体验版，拿到二维码

1. 开发者工具右上角「上传」→ 版本号填 `1.0.0`，备注随便 → 确定
2. 打开 https://mp.weixin.qq.com → 「管理」→「版本管理」→ 找到刚上传的**开发版本**
3. 点「选为体验版本」→ 生成**体验版二维码**（长期有效，可以截图）

### 第 8 步：把朋友拉进来

1. 后台「管理」→「成员管理」→「体验成员」→「添加成员」→ 搜朋友微信号添加
   - 上限 **60 人**，家宴远远够用
2. 把体验版二维码发到家庭群，或直接在小程序里点「···」→「发送给朋友」发分享卡片
3. 朋友扫码 → 自动进入点菜页 → 加菜、写备注、填昵称和人数 → 提交

> ⚠️ 关键点：**朋友必须是体验成员**才能打开体验版，否则会提示没有权限。所以先加成员，再发码。

## 四、功能清单

### 朋友端（不需要登录，扫码即用）
- 扫码/分享卡片进入，看到本次上架的菜（emoji + 菜名 + 描述 + 口味标签）
- 加减数量、给每道菜写口味备注（少辣 / 不要香菜 / 多放醋）
- 分类标签左右滑动快速找菜
- 提交时填昵称、到场人数、预计到达时间、整体备注（忌口）
- 提交后可随时改单（重新提交即覆盖），也可一键撤销
- **「大家都在点什么」（点菜页展开可见）**：朋友之间互相可见——每道菜共几份、都有谁点了，以及每个人带几个人、点了什么。展开时每 30 秒自动刷新；接口刻意不返回主人口令、订单 id、openid 等内部字段
- 菜品限量时会在提交时校验，被点完会提示「只剩 N 份」
- 截止时间到了自动锁单，只能看不能改
- **吃完给这一场的菜点赞（👍 卡片）**：**点一下就生效，没有"提交"按钮**——点中即记上，再点一下取消，最多 3 道。**不受点单截止时间影响**：吃完之后、甚至主人把菜全部下架了，照样能投（那时候才是投票高峰）。卡片上有一行「保存中…／已保存 ✓」的轻提示，保存失败会自动把勾退回去并说明原因
- **能看到自己参加过的每一场**：卡片上方是一排场次标签（`第 1 场` / `中秋家宴` / …），点一下就切到那一次去**补投或改票**。哪一场投过会标着「已投 ✓」，正在进行的那一场标「进行中」
- **去过几场就能投几次**：同一个人来了三次、每次都给「红烧肉」点赞，那就是 3 票——跨场次的累计数正是"老朋友都说好"的证据。而**同一场里还是一人一票**（反复提交只覆盖自己，不会把自己刷成 10 票）
- 菜品行上的 `👍N` 是**跨场次累计**（不是本场），新朋友点菜时最该看的就是这个

### 场次：一次家宴一盘账 🎊
> 这一版的核心概念。**每一场家宴 = 一个场次**，点单、点赞都按场次分开存，历史场次全部留着。

- **开始新的一场**：后厨看板顶部 →「开始新的一场家宴 ›」→ 给它起个名字（如「0913场家宴」）。序号自动 +1
- **改这一场的名字**：后厨看板顶部 →「✎ 改这一场的名字 ›」。只改名字，订单/点赞/库存毫发无损；历史场次的名字不会被串改
  - 也可以在云开发控制台直接改 `config` 文档的 `sessionName`：**当前这一场的名字以它为准**，`sessions[]` 里那条只是历史存档，所以不会出现"大厅改了、朋友端标签还是旧的"
- **开新场做了什么**：上一场的订单和点赞**原样保留**（朋友还能回去给那一场点赞，累计榜也不会丢）；「已采购」勾选重置（那是上一场买菜用的）；**家里的库存不动**；菜库的上架状态也不动（你自己决定今晚做什么）
- **看板默认只看当前这一场**：到场人数、份数、菜品汇总、食材采购都是"这一场"的账；上一场的数字不会混进来
- **想看以前那一场，点场次标签切过去**：看板顶部是一排场次标签（`0913场家宴（第 2 场）`、`周六家宴（第 1 场）`…），点一下就换成那一场的点单明细和点赞榜，**想看谁点了谁没点、谁赞了哪道菜，切过去就能看**。历史场次是**只看不改**（"不做"和改份数的按钮会收起来，免得手滑改到已经结束的家宴），顶部有「← 回到当前这一场」
  - 唯一不跟着切的是**食材采购**：买菜是给"现在"买的，所以回看历史场次时这块不显示
- **朋友的「我参加过的场次」**：去过的每一场都列在那里，点进去就能给那一次补投；**没参加过的场次投不了票**（服务端拦着）
- **开席了才能投票**：**有人点过单**才算这一场真的开了席。刚建好下一场时（还一个人都没点），朋友那边会提示「这一场还没开席」，投不了——不然你刚建好下一场，上一场的人顺手就能把下一场的票投了。**例外**：这一场你本来就已经有票了（比如早先版本留下的误投），那可以改也可以撤，不会把自己卡住

### 主人端（后厨看板）
- 到场人数、已下单人数、总份数、菜品种类四个数字（**都只看当前这一场**）
- **菜品汇总**：每道菜共几份、都有谁点了、每个人的口味备注、以及 **👍 本场几人赞**
- **👍 点赞榜（两张）**：
  - **本场榜**：这一场客人投的，按人数排序、前三名带奖牌、带进度条；**每道菜下面列出是谁赞的**（名字就是他点单时用的称呼）
  - **催票名单**：本场榜最下面一行「还没投的：老王、小李」——**这一场点过单、但还没投票的人**。开饭前挨个催一遍最有用
  - **🏆 累计榜（跨场次）**：去过几次就投几次票，所以"来过三次都说好"会排在前面。名字后面带 `×N` 表示他赞过 N 次。**下次家宴挑菜看这张**
  - 「清空本场点赞」只清本场，历史场次的票和累计榜不受影响
  - 「是谁赞的」**只有主人看得到**：朋友端的接口只返回人数，绝不返回姓名（有回归测试盯着）
- **按人明细**：谁带几个人几点到、点了什么、有什么忌口
- **三种导出（都不含「谁点的」）** —— 各复制各的，粘到群里或发给家人：
  - 「**复制菜单（发客人）**」：按分类列菜名 + 标题和地址，像一份正式菜单
  - 「**复制菜 + 食材**」：每道菜带份数和它的食材（自己备菜用）
  - 「**复制待购食材**」：只列**还要买**的（已经扣掉家里本来就有的），买菜照着买
- **食材采购清单**：按今晚的菜单（已上架的菜 + 已点过的菜）自动聚合去重，每项显示"被哪些菜用到"；**买到了点一下划掉**。清单自动分成三档：`还要买` / `已买` / `家里有`，家里有的排最后并带「🏠 家里已经有，不用买」标记，**不计入"还要买"**
- **下单期间每 2 秒自动刷新**（朋友那头点一下，你这里几乎立刻能看到）；离开页面自动停止，**截止后会降频到 15 秒**——那时谁也改不了单，没必要烧云函数调用次数。也可以下拉刷新
- **调整点单（三种操作）**：
  - 「菜品汇总」里每道菜右侧「**不做**」→ 从**所有人**的订单里去掉它，并自动下架（免得又被点回来）
  - 「按人明细」里每项右侧的「**×N**」→ 点它把份数改成**精确值**（朋友误点 8 份，填 2 就完事；填 0 等于去掉）
  - 「按人明细」里每项右侧「**−**」减一份、「**✕**」整条去掉
  - 改完如果那一单空了，整单删除（不留 0 道的空单把"到场人数"算多）；被改动的朋友打开「我的点单」会看到「主人去掉了：XXX」或「主人把 XXX 改成了 ×2」，他重新提交后提示自动消失

### 主人端（家里的库存 🧺）
> 记的是「**我家现在有什么**」，**跟菜谱完全无关**：酱油剩半瓶、冰箱里有排骨、冷冻层塞着饺子，都可以录进去。它不参与点单，只在两个地方起作用：挑菜时告诉你"这道菜家里缺几样"，买菜时把家里已有的从待购清单里划掉。

- **录入**：名称 + 分类（食材 / 调料 / 其他）+ 数量（随便写，`2 瓶` / `半袋` / 留空都行）+ 备注（`放在灶台下柜子`）
- **点一下就能记**：菜谱里出现过的 93 种食材列成一片可点的小标签，**点一下 = 家里有**（再点一下取消）。这比一个个打字快得多，而且名字跟菜谱逐字一致，交叉比对不会因为错字失效；上面还有搜索框
- **批量粘贴**：一行一样，`生抽 2瓶` / `五花肉，1斤` / `小葱` 都能认；自动跳过 `#` 注释、序号、项目符号，重复的只留第一条，并顺手猜好分类（调料 / 食材）
- 点任意一行可以改数量、备注、分类；`✕` 删除；「清空库存」整体重来
- **交叉联动**：
  - 「家宴设置与菜库」里每道菜名下会显示 `✅ 食材都有` 或 `🧺 缺 3 样`，点一下能看到**具体缺哪几样**，并可直接跳去补库存；页面顶部还会告诉你"有 N 道菜的食材家里已经齐了"——照着这个挑菜最省事
  - 「后厨看板」的待购食材会自动扣掉家里已有的
- 库存**只有主人看得到**：朋友端的接口不会返回它（家庭物资情况没必要发给客人）

### 主人端（设置与菜库）
- 改标题 / 主人称呼 / 地址 / 提示语 / 点单截止时间（开关式）/ 每单最多点几道
- 69 道菜谱一键导入（每道菜带食材）（只补新增，不覆盖你改过的）。要改菜谱就编辑 `miniprogram/data/dishes.seed.js`，然后 `node tools/make-import.js` 会校验并生成控制台导入文件
- **挑下次的菜单时有两条参考**：每道菜名下的 `👍N`（**跨场次累计**票数）和 `✅ 食材都有 / 🧺 缺 N 样`（家里够不够做）；页面顶部还会列出"累计最受欢迎的几道"
- **「补全食材」**：给菜库里已有的菜只补 `ingredients` 字段，**不动你的上架状态、限量、改过的描述**（老菜库升级用；这个按钮跟库存无关）
- 整组上架/下架、全部上架/下架、逐道开关
- 逐道设置限量份数、删除菜品、临时加菜
- **✎ 编辑菜品**：每行菜名右边点 ✎ 就能改**菜名 / 分类 / 简介 / 图标 / 食材 / 标签**
  - 临时加的菜（「+ 新增」）默认落在「自定义」分类，用这个把它挪进 **猪肉 / 蔬菜 / 主食…** 任意分类
  - 食材写全了，才会跟「家里的库存」比出「✅ 食材都有 / 🧺 缺 N 样」
  - 编辑**不会动**上架状态和限量（限量还是在列表里的「份」框改）
- 显示主人口令（配偶输一次也能成为主人，一起看汇总）

```

├─ project.config.json          小程序项目配置（AppID 会被工具改写）
├─ cloudfunctions/
│  └─ api/                      唯一的云函数，所有接口走 action 路由

├─ miniprogram/
```

## 六、数据模型（云数据库）

| 集合 | 说明 | 主要字段 |
|---|---|---|
| `dishes` | 菜库 | `name` `category` `desc` `emoji` `limit`（null=不限）`tags[]` `ingredients[]`（食材）`sort` `available` |
| `orders` | 点单（**一场一人一单**） | `_openid` `sessionId` `sessionNo` `sessionName` `nick` `partySize` `arriveAt` `note` `items[{dishId,name,emoji,qty,note}]` `totalQty` `createdAt` `updatedAt` |
| `votes` | 点赞（**一场一人一票**） | `_openid` `nick`（提交时的昵称快照）`sessionId` `sessionNo` `sessionName` `items[{dishId,name,emoji}]`（最多 3 条）`createdAt` `updatedAt` |
| `config` | 家宴配置（单文档 `party`） | `title` `host` `address` `notice` `deadlineTs` `maxDishesPerOrder` `hostCode` `admins[]` `shopping{}`（已采购的食材）`pantry{}`（家里的库存）`sessionId` `sessionNo` `sessionName` `sessions[]`（场次列表） |

> **老数据兼容**：`sessionId` 是后来才加的字段，**历史订单/点赞没有它**。代码里把"缺这个字段"等价于第 1 场（`sessionId === 'party'`），所以老环境升级上来历史数据会自动归位到第 1 场，**不需要跑任何数据迁移**。

`pantry` 的结构是 `{ "生抽": { cat: "调料", qty: "2 瓶", note: "灶台下柜子" }, ... }`。
为什么塞在 `config` 里而不是单开一个集合：库存天然是"一份"而不是"很多条记录"，塞进来还省得再建集合，也就没有多一个集合权限要操心。

设计上的两个要点：

1. **所有读写都走云函数**，云开发控制台的集合权限不用动（保持默认即可），也不会出现「客户端能改别人的单」这种越权问题。
2. 集合和初始配置由云函数自动创建（`init` 时 `createCollection`），所以你**不需要在控制台手工建集合**。
3. `votes` 是后来才加的集合，**老环境里没有**——而 `init` 只在「开通家宴」时跑一次。所以点赞的写入做了兜底：**集合不存在就自动补建一次再重试**，不用你手动去控制台建。

## 七、常见问题

**Q：报错 `Cannot read properties of null (reading 'admins')`**
旧版本云函数的问题（`saveConfig` 错误地依赖了 `doc().update()` 在文档不存在时抛异常）。**重新上传部署一次云函数即可**，当前代码已修好并加了回归测试。

**Q：输入框里的文字掉到框下面一半，点一下才正常**
小程序 `<input>` 是原生组件，**垂直方向的 padding 会让文字渲染错位**。当前代码已改成「显式 `height` + 只保留水平 padding」。如果你自己改了样式，注意不要在 input 上加 `padding-top/bottom`——`node tools/check.js` 会拦住这种写法。

**Q：什么时候该点「开始新的一场家宴」**
下次请客之前点一次。它给新的一场起个名字并 +1，上一场的订单和点赞**留着**（朋友还能回去补投、累计榜不丢），同时把「已采购」勾选重置掉。菜库和家里的库存都不动。
**Q：为什么看板上看不到上次家宴的订单了**
那些订单没删，只是属于上一场。看板默认显示**当前这一场**；点顶部的场次标签（如「周六家宴（第 1 场）」）就能切回去看那一场的点单明细和点赞榜，看完点「← 回到当前这一场」。历史场次是只看不改的。

**Q：刚建好下一场，朋友就能给下一场投票了？**
不会。**有人点过单**才算这一场开了席；还没人点单时朋友那边只会看到「这一场还没开席」，投不了。

**Q：打开「家里的库存」提示「未知操作：listPantry」，或者菜单页提示「没读到库存」**
云函数还是旧版本（没有库存相关的 `listPantry` / `savePantryItems` 等 action）。**重新上传部署一次云函数即可**；菜单页即使读不到库存也照常能用，只是不显示"缺几样"。

**Q：库存和「补全食材」是一回事吗**
不是。
- **库存**（`我的点单 → 家里的库存`）记的是**我家现在有什么**，跟菜谱无关，你自己随手录；
- **「补全食材」**（`家宴设置与菜库`）是给**菜谱**补 `ingredients` 字段，也就是"这道菜要用什么"，是菜谱的一部分。
两者只有名字相同，交叉比对时按**名字完全相同**来匹配。

**Q：为什么待购食材清单里的东西家里明明有**
比对是**逐字同名**的：`小葱` 和 `葱`、`生抽` 和 `薄盐生抽` 会被当成两样。这是有意的——宁可多买一次，也别把不一样的当成一样的。想让清单更短，就在库存里按菜谱里的写法点一下（库存页的「从菜谱食材快速点选」列出的名字跟菜谱逐字一致）。

**Q：开通成功了，但找不到主人口令 / 找不到导入菜库的入口**
主人口令和「家宴设置与菜库」都在**「我的点单」标签页**的「主人控制台」卡片里。当前版本在开通成功时会**直接弹窗显示口令**，点菜页顶部也有「家宴设置与菜库 ›」入口。

**Q：提示基础库版本过低 / 云能力不可用**
开发者工具 →「详情」→「本地设置」→「调试基础库」选 **2.2.3 以上**（推荐直接选最新稳定版）。`project.config.json` 里预置的是 `3.5.5`，如果你的工具里没有这个版本，工具会自动回退并提示，手动选一个最新版即可。

**Q：编译后提示「云函数 api 还没部署」**
按第 5 步上传部署云函数。如果右键没有「上传并部署」，先点工具栏「云开发」完成授权。

**Q：导入菜库报超时**
云函数默认超时是 3 秒，去控制台把 `api` 的超时时间改成 20 秒（见第 5 步第 3 点）。代码里已经做了并发写入，正常 1～2 秒能完成。

**Q：朋友扫码提示没有权限**
说明他不在体验成员名单里。后台「成员管理 → 体验成员」把他加上，再让他重新扫码。

**Q：能用开发版的预览二维码吗**
不建议。开发版预览二维码有效期只有几十分钟，第二天就失效。体验版二维码是长期有效的。

**Q：上传时提示要先完善基本信息**
按提示填小程序名称、头像、简介即可。类目可以先不填——体验版不走审核，不影响使用。

**Q：以后还想用怎么办**
这套东西是通用的：下次家宴只要在「家宴设置」里改标题和截止时间、重新勾选上架菜品，新朋友加为体验成员就行。菜库会一直留着。

**Q：数据在哪里**
微信开发者工具 →「云开发」→ 数据库，能看到 `dishes` / `orders` / `config` 三个集合的原始数据，也可以直接导出。

|---|---|---|
| `tools/check.js` | JS 语法、JSON 合法性、页面文件齐全、WXML 标签平衡、前后端接口名一致性、菜库种子格式、WXML/WXSS class 一致性、**wx:for 必须带 wx:key**、input 垂直对齐防护 | **全部通过** |
| `tools/test/integration.js` | 用本地 mock 的云开发环境真跑云函数，走完整业务流程；再加载 5 个页面并验证前端纯逻辑；含 SDK 行为差异的兼容性回归 | **全部通过** |

> 判定标准看脚本末尾那行「通过 N 项，失败 0 项」——**这行是唯一可信的计数**，会随检查项增加而变化（写作时为静态 109 项、集成 439 项）。

集成测试真正验证过的行为（这些不是"看起来对"，是跑出来的）：

- 全新环境下主人点「一键开通」直接成为管理员，并自动生成 4 位主人口令
- 朋友进来的身份是客人，**看不到主人口令**，也调不动任何管理接口
- 导入 69 道菜 → 菜库默认全部下架（朋友端看不到）；朋友端只拿到已上架的菜，重复导入不会产生重复数据
- 主人端改份数：3 份改成 1 份后朋友端立刻看到新份数与"主人把 X 改成了 ×1"的说明；改到 0 份等于去掉且空单被删；份数被夹在 0–99；**漏传份数会被拒绝**（否则漏参数会被当成"减成 0 份"误删）
- 主人端去掉菜品：只影响指定那一单 / 影响所有单（并从所有单去掉时自动下架该菜）；空单整单删除；朋友重新提交后"主人调整过"的说明自动清掉
- 朋友端的「大家都在点什么」不需要主人权限；接口不返回主人口令 / 订单 id / openid，且与主人看板共用同一份聚合逻辑（不会出现两边数字不一致）
- 限量规则：手工水饺限 4 份，老王点 2 份后，小李点 3 份被拒并提示「只剩 2 份了」
- 重复提交是**覆盖**自己那一单，不会在汇总里变成两个人
- 已截止、已下架的菜都会被服务端拦下；截止后仍能查看自己的单
- 删除某道菜后，历史汇总里仍能看到它的菜名和份数（不会丢数据）
- 超长昵称/人数/备注会被裁剪，极端输入不会写坏数据
- 看板复制出来的文本格式正确（菜品清单 + 每道菜的口味备注 + 按人明细 + 忌口）
- 购物车合计按整个购物车计算，切换分类不会让底部「已点 N 道」错误归零
- 看板自动刷新定时器：重复启动不会泄漏出第二个定时器，离开页面（onHide/onUnload）一定会被清掉
- **云开发 SDK 两种行为下初始化都不崩**：`update` 在文档不存在时「抛错」和「静默返回 `stats.updated = 0`」都测了（线上第一次初始化崩溃就是栽在后者）
- 半成品配置（有文档但一个管理员都没有）能被第一个到达的人认领，不会出现「谁也进不去」
- 样式防护：WXML 里用到的 class 必须在 wxss 里有定义；用在 `<input>` 上的 class 必须有显式 `height` 且**不能有垂直 padding**（原生组件垂直 padding 会让文字掉到框外）；每个 `wx:for` 都必须带 `wx:key`
- 看板按人明细的渲染 key 是**下标派生的唯一值**，不是昵称——家宴里两个人把昵称写一样不会导致列表渲染错乱
- 点菜页的截止状态每 30 秒本地重算一次（不发网络请求），并且**点「提交点单」时会用"现在"再判一次**，不会出现"填完整张单子才被拒绝"
- **点赞是"一场一人一票"**：同一场里重复提交会**覆盖**（不是累加），所以本场榜不会被同一个人刷高；传空数组 = 撤销且幂等（没有票时再撤也不报错）
- **跨场次是累加的**：同一个人在 3 场里都投了同一道菜 → 累计榜 3 票。这正是要的（"来过三次都说好"），也是本场榜和累计榜必须分开的原因
- **场次隔离**：开新一场之后，看板和「大家都在点什么」只看当前这一场；上一场的订单**不删**（朋友还能回去给那一场点赞），但**不会混进本场的数字**
- **看板能回看历史场次**：`summary` 带 `sessionId` 就按那一场算（点单明细、点赞榜、催票名单都跟着切），返回里带 `isCurrent: false`；**食材采购永远按当前这一场**——测试里专门验了"回看第 1 场时点单是那一场的份数（×1），而食材统计仍等于当前第 2 场的"
- **催票名单按 openid 判，不按名字**：「这一场点过单、还没投票的人」用 openid 比对。按昵称比对会出错——点赞时没填名字的人存的是占位「匿名朋友」，会被列成"还没投"，其实他投过了
- **只有参加过的场次才能投票**：服务端会拒（"这一场家宴你没参加过"）；当前这一场本人没点单也能投 —— 但**得有人开席**（这一场有人点过单），否则一律拒投并提示「这一场还没开席」
- **没开席时不发候选**：`votes` 返回 `started: false` / `canVote: false` / 空候选，朋友端显示"这一场还没开席"。**已经投过票的人例外**：票照旧返回（看得见、改得动、撤得掉），否则他连取消都做不到
- **朋友端的场次标签过一层映射**：接口的场次描述里字段叫 `id`，模板里用的是 `sessionId`，所以 `mapDinners()` 负责把这一层对上。这条是踩出来的：直接塞原始数据时标签名字显示得出来、**点上去却什么都不发生**（`data-id` 是空的），测试里现在拿 `myDinners` 的**真实返回**过一遍这个映射，id 丢一个就会红
- **老数据不串场**：历史订单/点赞没有 `sessionId` 字段，代码等价成第 1 场——测试里专门塞了一条没有 `sessionId` 的订单，验证它出现在第 1 场、**不会跑到第 2 场去**
- 回旧场次改票只影响那一场（改完本场的票不动）；「清空本场点赞」只清本场，累计榜不受影响
- **点赞不受截止时间限制**，而且**菜被主人全部下架之后照样能投**——候选名单取自「这一场订单里出现过的菜 ∪ 我投过的菜（∪ 当前场次的上架菜）」，正是为了覆盖"吃完才投、而主人已经下架"这个真实场景
- 投票会**去重并忽略不存在的菜**，且**超限判断放在去重之后**（客户端传了带重复的数组不该被误判成"投了 4 道"而拒绝——这条是测试逼出来的）
- 点赞的写入带**集合自动补建**：老环境没有 `votes` 集合时，第一次投票会自动建好并写入成功，而不是报 `collection not exists`
- **主人能看到每道菜"是谁赞的"**：投票时带上当时的昵称（存在票上，跟订单一样是快照）；**没填名字（存的是占位「匿名朋友」）或老记录里没有昵称的，都用"他那一场的点单昵称"兜底**，不会显示成匿名、也不会同一个人被拆成两个名字。同一个人在两场都赞了同一道菜，累计榜里合并成一条 `×2`
- **「是谁赞的」绝不发给朋友**：`board` 与 `votes`（朋友端用的接口）都不含 `who` 字段，只有 `summary`（主人专属）才带
- 投票时会顺手把昵称存到本地；没留名字也能投，卡片上会提示一句「主人看不到是谁赞的 —— 点这里留个名字」（**不弹窗拦人**，点赞就该是点一下的事）
- 朋友端能看到「几人赞」（这是"老朋友推荐什么"的意义），但接口**不返回别人的 openid**；配置里也不会带出投票内部字段
- **库存跟菜谱解耦**：库存里塞与菜品无关的东西（咖啡豆、猫粮）不会影响采购清单；库存**不会把食材从清单里删掉**，只做标记，所以"这次要用到什么"永远看得全
- 库存的"家里有 / 已买 / 还要买"三个数**加起来正好是总数**，不会重复计数（既勾了已采购、又是家里有的，只算「家里有」）
- 库存更新时**没传的字段保持不变，传了空字符串才是清空**——「快速点选」这种只带名字的调用不会把已有条目的数量、备注抹掉（这条是被测试逼出来的：最初的实现会静默清空）
- 批量粘贴能正确处理 `生抽 2瓶` / `五花肉，1斤` / `- 小葱` / `1. 生姜` / `# 注释` / 空行 / 重复条目
- 菜单页的"够不够做"：只做**同名匹配**，不猜同义词（`小葱` ≠ `葱`）——宁可多算一样缺的，也不自作聪明把不一样的当成一样的；没配食材的菜**不会**被误报成"食材都有"；**库存是空的（或没读到）时一律不显示**，否则满屏"缺 N 样"既像噪音又像数据丢了
- 库存是**主人独有**的：朋友调用 `listPantry` / `savePantryItems` / `clearPantry` 一律被拒，`whoami` 返回的配置里也没有 `pantry`
- 旧版云函数（没有库存相关 action）不会把菜单页搞崩：库存读不到只是不显示"缺几样"，并提示可能还没重新部署
